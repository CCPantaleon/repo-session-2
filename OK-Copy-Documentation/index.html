Repository guide

OK, Copy — Verified Copying Tool Technical white paper and operating reference · v3.7, build 13 · October 30, 2026

OK, Copy is a native macOS utility for copying regular file contents from folders, camera cards, and local drives to one or more destinations, with independent SHA-256 readback, interruption recovery, and saved reports. This repository documents the delivered implementation; it is not a performance advertisement or a certification of hardware reliability.

Beginner's quick start

This guide uses the controls in OK, Copy 3.7. Start with generated samples so you can learn the interface before selecting a real card.

1. Prepare the Mac and folders

Use an Apple silicon Mac running macOS 14 or later. The packaged app runs without Xcode or a separately installed Swift toolchain. Quit an older copy before launching the new build. The development release is locally signed and is not notarized; if deployment is blocked, obtain a trusted distribution build from the maintainer rather than disabling system-wide security.

For a real transfer, connect your reader and intended destinations. Create destination folders in Finder first if needed: the destination picker selects existing folders. One destination on the internal SSD is supported. A second independent drive gives a different kind of protection from a second folder on the same drive.

Close applications that might still be recording into or editing the selected source. OK, Copy protects its own source access; it does not prevent another application or the operating system from using a mounted card.

2. Try a harmless sample

  1. Launch OK, Copy and wait for Safety checks passed.
  2. Choose File > Try Sample Copy. This generates sample files and temporary destination folders; it does not use your selected camera originals.
  3. Inspect the two sample sources on the left and the destinations on the right.
  4. Read the folder diagram to see what will be created. If preferences restored another layout, select Organized: Originals > Source Folders for this exercise.
  5. Choose Review Copy if you want to inspect a dry-run report first. It is optional.
  6. Choose Start Copy. The Transfer Queue opens and shows each destination's copy and verification progress.
  7. Wait for Completed and Verified results, then open Report.

New successful destination reports display Verified in green. Missing/unverified results and failures appear in red with text explaining the condition. The report opens in its own resizable window.

A sample safety check and Try Sample Copy serve different purposes. The automatic safety check tests generated fixtures before enabling normal copying. Try Sample Copy is an interactive demonstration that lets you learn the same controls used for actual jobs.

3. Select real sources

Choose Add Folders… on the left, or select a detected external volume under Connected Drives. You can select several source folders. An external volume with a DCIM folder is labeled as a detected camera folder; that is a folder heuristic, not proof of the device model or health.

Adding your own source after the sample replaces the sample selections. Check the source path, file count and total size. Expand File preview for a thumbnail where Quick Look supports it. Use the source list to switch between sources.

Filter files only filters the displayed list. It does not exclude files from the job. The app copies the selected folders' included regular files. Select a narrower source folder if you need a narrower operation.

A source label identifies the source's output folder when that layout uses one. Labels must be unique and valid formatted identifiers. If a source name contains spaces, the proposed label may use hyphens. For one-source flat layouts the label is unused in the visible mapping, although the planner still validates it.

4. Choose destinations and layout

Choose Add Destination… and select one or more existing folders. Read the actual paths, not just volume names. The app allows an internal destination, a working SSD, or several local destinations. It rejects destinations that overlap a protected source or one another. A selected external source volume is protected as a whole; another folder on that same volume is not a valid destination.

Optional MHL export is under Camera options. Enable Export MHL + ASC MHL only if you need those interchange files. SHA-256 copy verification and HTML/JSON reports are present without that option. Exported ASC MHL is a flat inventory, not a complete custody history.

6. Review, copy now, or queue

Review is useful when you want a conflict report before any destination files are written. It usually takes additional reading time; skipping it does not disable verification. With Skip verified matching files enabled, existing intended files are rehashed before being reused. Different content at the same path is a conflict, not an instruction to overwrite it.

Start Copy can be disabled while required choices are missing or sample safety checks have not passed. Read the inline explanation. If planning still reports an invalid label, collision, read-only destination or space problem, correct the named choice before retrying.

7. Read progress correctly

The queue shows written/readback bytes, separate copy and verification bars, recent copy/readback speeds, average combined I/O, elapsed time, phase and errors. Current speeds become zero after a job stops; historical average I/O is a different metric.

An estimate needs a warm-up period. It includes modeled source reads and publication work, but can change with hardware contention, read errors, caching and finalization. Cascading initially estimates backup work from the working destination's rate. A future unstarted queue has no promised completion time.

A success count applies to actual destination outcomes. “2 of 3 destinations verified” means the healthy copies should remain available while the third needs attention. Read each destination's error; do not treat a general queue failure as proof that every copy is corrupt.

8. Stop, reconnect and resume

Choose Stop/Pause Queue to request a safe stop. Blocking device I/O may delay the response. Wait for the paused state before disconnecting a drive when possible. If you quit while work is active, choose Pause and Quit to let the app finish stopping before it exits.

After interruption, restore the original source and destination locations, then use Resume on the affected job. The app rechecks existing full files and saved partial prefixes; it does not trust the old percentage. A replaced destination with the same name may be rejected because its identity differs. Do not rename/move private workspaces to trick the identity check.

When cascading has reached Working copy verified · backups pending, the backup stage can use the verified working copy. The card is no longer needed by that job's backup stage, but the working destination must stay available and pass its checks. This is not an instruction to erase the card.

Forget removes the queue entry only. It does not delete destination files or retained partials. Keep the job and its hidden .OKCopy data while recovery may still be needed.

9. Open, export or reverify a report

Choose Show Saved Reports. History shows project, date, destinations and outcome, with Open, Export…, Reverify… and Show in Finder actions. It discovers app-local reports and locations referenced by saved jobs; it is not a search of every drive.

Open displays the saved event in a resizable window. Export saves an HTML copy to a chosen location; that action does not necessarily export the companion JSON receipt. Preserve the JSON too if you want the app's structured SHA-256 re-verification input. Optional MHL files are another interchange route.

To check files now, use Verify Manifest… at the top, or Reverify… for an eligible history item. Select an MHL/JSON receipt and the folder from which its listed relative paths resolve—normally the project root, or the selected destination root for direct copying. Selecting the Ingest Reports folder as the content root is usually incorrect.

Reverification only certifies listed data forks it can check. Unsupported entries, missing files or hash mismatches require attention. Historical Verified reports do not become current verification merely because you open them again.

10. Recover a report-only failure

If the media is verified but report export failed, reconnect the report location and use Retry Report Export on the failed job. An eligible frozen pending receipt can export without reading the original card or copying media again. No pending record means there is nothing for that particular recovery action to export.

Manifest-generation failures and incomplete media copies need Resume rather than report-only recovery. If you need current integrity evidence after an export retry, run Reverify separately: the recovered report describes the original verification event.

Working vocabulary

Source: the selected original folder/card. Destination: a selected folder receiving a copy. Project: a named output root when the layout creates one. Checksum: a content-derived fingerprint. Readback: a separate read of written destination data. Incremental: reusing matching intended paths and adding new files. Cascading: creating backups from the verified working destination. Receipt: saved evidence of a verification event. Manifest: a machine-readable list of paths and checksums.

White paper

OK, Copy 3.7 · build 13 · implementation reference dated October 30, 2026

Executive summary

OK, Copy is a focused, native macOS verified-copying application. Its central operation is a saved copy job: selected source folders, intended output paths, chosen destinations, verification policy, and report placement are recorded before transfer. The app copies regular file contents, verifies each destination against source SHA-256 references, and keeps enough private state to recheck and resume interrupted work.

The product grew from a photography ingest workflow into a more general verified copying tool. It supports photos, video, sidecars, and other regular files; file extension does not determine whether a file is copied. One internal destination is valid. Two folders on the same disk are also allowed, although they do not constitute independent protection against that disk failing.

Its most useful distinction is the integration of a narrow safety policy, visible verification, recoverable partial files, and user-readable receipts in a small source-included app. It is not established to outperform professional offload software, and its current validation does not establish equivalent field maturity.

What Verified means

For an ordinary successful copy, the engine hashes a source read while sending chunks to destination writers, flushes each staged copy, reads that staged copy back, compares its SHA-256 to the source digest, rereads the source, and checks that the source still matches. The final file is then published without replacing unrelated destination data. Additional validation applies when publication itself needs a compatible copy operation.

Review Copy establishes a pre-transfer baseline. Start Copy can instead establish the baseline during the transfer. For that immediate mode, write-once source references are saved in destination-owned recovery workspaces before final-file publication. Subsequent attempts compare against these references; they do not silently redefine the original checksum to match changed content.

A Verified destination receipt refers to that destination's completed verification. A job succeeds only when its required copies and completion steps succeed. A report/export problem can leave valid, published files while the queue still requires attention. Receipts distinguish destination-specific outcomes from all-destination completion.

A checksum comparison is evidence about byte equality at a particular time. It does not certify the camera's recording, exclude pre-existing corruption, establish copyright or chain of custody, or predict a memory card's remaining life. A second read through macOS can be served partly from caches; independent readback is a separate read operation, not a claim that every byte was retrieved freshly from the physical NAND.

Architecture and transfer modes

The GUI uses AppModel to prepare and save immutable plans. TransferEngine applies a startup generated-file safety gate and delegates to ManagedTransfer. That coordinator owns source work, per-destination writers, checksum checks, publication, and reporting. SafeIO provides anchored path traversal and exclusive destination creation. StorageScheduler uses available macOS topology information to limit contention on detected shared resources.

In direct mode, one streamed source-copy pass fans chunks out to independent bounded destination queues. This avoids reading the card once per destination during that pass. It does not mean a file is read only once overall: source rechecking, optional Review Copy, prefix validation, and cascading add reads. Short writer stalls can be buffered; a sustained slow writer eventually applies backpressure to the shared source stream.

In cascading mode, destination 1 is the working copy. After that copy is verified and published, its planned files are checked again and used as backup sources. This can release the original card from the backup stage sooner. It shifts later read load to the working drive; it does not guarantee the shortest total completion time.

Non-destructive source policy

The app does not expose erase, format, repair, or move-original operations. Source contents are opened read-only. Source links and special files are rejected, destinations cannot overlap protected sources, and external/removable source volumes receive broader protection than a single selected subfolder. Reports and queue storage are also checked against protected locations.

This is an application policy, not a hardware write blocker. macOS and other applications can still access a mounted card; automatic filesystem activity is outside this program's guarantee. The app also cannot make two destinations physically independent merely by assigning different folder names. Those distinctions matter when interpreting “source files stay untouched.”

Where this app offers a practical advantage

Compared with Finder

Apple documents Finder drag-and-drop as a general file movement/copying interaction. OK, Copy adds a specific ingest workflow: saved plans, several destination outcomes in one job, fixed checksum acceptance, private recovery state, and machine-readable receipts. That is an operational advantage for a user who needs evidence of copying. It is not a claim that Finder's internal copy implementation has no integrity checks or that Finder cannot run multiple copies. Finder remains the broader tool for ordinary file management. Apple Finder guidance

Compared with rsync

Rsync already has transfer verification: its manual distinguishes the normal transferred-file checksum from the pre-transfer --checksum decision. It also offers local/remote copying, partial-transfer options and broad metadata controls. OK, Copy's advantage is an integrated GUI policy and reporting workflow, rather than a claim that rsync lacks checksums. Rsync is more flexible for scripting, network synchronization and mirroring. Its installed version and options matter; current upstream documentation does not describe every macOS-bundled binary. Rsync manual

OK, Copy also avoids the need for an operator to construct several commands, choose potentially destructive synchronization flags, and assemble a separate report system. A carefully engineered rsync wrapper could supply many of those same workflow benefits.

Compared with Hedge OffShoot

Hedge documents configurable verification modes, including full source-and-destination readback. OK, Copy instead makes SHA-256 destination acceptance part of its fixed ingest policy. This reduces configuration ambiguity for this particular workflow; it is not a claim that OffShoot cannot verify destinations thoroughly. OffShoot verification

A concrete distinction is partial-file handling. Hedge's documented Stop & Resume workflow restarts incomplete files rather than resuming inside them. OK, Copy can recheck a retained partial prefix and append the remaining content, then verify the whole result. Its benefit depends on a valid retained prefix and storage conditions; this is not a timed comparison. OffShoot Stop & Resume

Hedge documents duplicate skipping based on destination path, size and modification date; OK, Copy rehashes intended existing paths before accepting a skip. That trades additional reading for content-based confidence. OffShoot also has wider production workflows and ASC history handling that this application does not reproduce. Duplicate detection, verification and ASC history

Compared with OWC Copy That

OWC documents multiple destinations, several hash choices, presets, job archives, MHL, and PDF/TXT/CSV reporting. Those are shared or broader capabilities, not unique advantages of OK, Copy. This app's reasons to choose it are its inspectable source-included policy, fixed SHA-256 ingest acceptance, three tailored layouts, and its particular recovery implementation. Copy That offers richer documented report/media workflows; no controlled comparison establishes which product is faster or more reliable. OWC Copy That, OWC support

The proprietary internals of the commercial products were not inspected. Claims about their private threading core, filesystem optimization layers or TCP tuning are therefore not inferred from feature names or marketing descriptions.

Performance and reliability boundaries

There is no valid performance ranking among these products in this repository. Old cached sample experiments are not sustained card benchmarks, and vendor speed claims use their own test conditions. The app's 8 MiB chunks, bounded queues and controlled concurrency are design choices, not evidence of a particular MB/s rate.

New immediate jobs normally require two full source reads: the streamed copy/hash pass and source reread. Review normally adds another full source read before execution. Each new destination receives a write and readback. Compatible publication can add a staging read, final write and final readback. This additional I/O is the cost of the chosen verification/publication policy.

Local signing and 67 automated tests do not establish safe behavior under every power interruption, storage bridge, filesystem, media defect or macOS release. The current record covers generated data; large real SD/CFexpress transfers, physical interruption qualification, comprehensive accessibility checks, and notarized clean-Mac distribution remain outstanding. See Validation and limitations.

Appropriate use

Use OK, Copy when you want a focused, inspectable local verified-copy workflow and can evaluate its development-stage qualification honestly. Keep originals until your independent copies and broader backup policy are satisfied. For production requirements involving full ASC custody, specialized camera SDKs, remote storage or vendor-backed hardware qualification, compare the requirements explicitly instead of treating a similar feature name as equivalent implementation.

Apple documents incremental hash updates in CryptoKit. That supports chunked operation; it does not justify claiming that Swift removes all unsafe memory handling. This code deliberately crosses into POSIX APIs, uses locks, and marks some shared types @unchecked Sendable; those areas require continued review.

Why not simply combine rsync, fcopyfile and FileManager?

They are different abstractions. Swift is the implementation language; Darwin calls are native macOS/Unix I/O; fcopyfile is another native copying primitive; rsync is a separate synchronization program. “Native engine” is not a single competing product or a security level.

Apple's copyfile/fcopyfile API provides copying, metadata options and callbacks, with documented cloning-related options. Those capabilities are useful primitives, but do not independently provide this app's job queue, multi-target failure policy or saved verification references. The shipping coordinator does not call fcopyfile as its transfer backend. Apple copyfile manual

Adding several backends would require equivalent verification, source protection, resume journals, publication behavior, cancellation and report semantics for each. A faster unverified path would change the product's contract. A high-level copy may also require a separate checksum read and cannot automatically share one streamed source pass among several independently managed writers.

Rsync can be a good backend for another design, especially remote synchronization. Here it would add a process boundary, version/option interpretation, and status mapping while the application still needs its policy layer. This is a rationale for the current implementation, not evidence that rsync is inherently less secure or slower. See the comparison for the distinction between its pre-transfer and transferred-file checksums.

The engine does not treat hard links or filesystem clones as separate backup copies. Sharing an underlying file or copy-on-write extents on one storage device is a different operation from writing and checking another destination. Independent file paths also do not by themselves establish independent hardware fault domains.

The historical fcopyfile comparison tool remains in Tools/CompareEngines.swift. A small cached test does not select the fastest engine for SD, CFexpress, USB, APFS, exFAT or network hardware. No multi-engine automatic selector is implemented.

Planning and output mapping

CardScanner enumerates directories with descriptor-based traversal. It accepts regular files, rejects links/special files, and sorts the file inventory. Known housekeeping exclusions are explicit rather than a blanket “skip all hidden files.” Source root protection is broader for externally mounted volumes, including when only DCIM is selected.

BatchPlanner refreshes inventories, validates source labels, creates destination identities, computes intended paths, rejects collisions, and checks required capacity. Names are compared conservatively with normalized, case-insensitive keys so a plan cannot depend on a case-sensitive destination to keep otherwise-colliding files distinct. Source labels are formatted identifiers; project folder names are exact user text subject to validation.

These are preflight estimates; free space can change during a transfer.

Optional review versus immediate copying

A reviewed job uses plan schema 2, containing precomputed SHA-256 references. Review scans and hashes source files, checks intended existing copies, identifies duplicate content, and produces a dry-run report without creating destination media files. Temporary app-side review artifacts can still be written.

An immediate job uses schema 3 with hashDuringCopy = true. It performs path/inventory/capacity preparation but leaves file hashes unresolved until the streamed source read. It then saves each resolved reference through SourceChecksums before publishing the corresponding final media file. Those references are written once and compared on resume.

Review improves observability before writes; it is not required to turn on SHA-256 verification. It normally adds I/O, so it should not be marketed as a speed optimization. An unstarted immediate plan cannot establish the byte contents before its first actual source read: identical size/time metadata alone is not a cryptographic baseline.

Execution and integrity sequence

For each file, the shipping path proceeds through these steps:

  1. Reopen the source read-only and check its current stamp against the refreshed inventory.
  2. Load any saved source references from healthy job workspaces; incompatible references abort source acceptance.
  3. Rehash existing intended destination files, or validate retained partial prefixes against the source. Preserve invalid partials under rejected names before restarting.
  4. Read and hash source chunks through a bounded pipeline; fan chunks out to destination-specific writer queues, skipping already retained valid prefixes where appropriate.
  5. Join writer operations and check source stamp, stream length and any existing expected hash.
  6. Save resolved source SHA-256 references in healthy workspaces before final-file publication.
  7. Apply modification times to staged files, flush, read back each new staged copy, and compare SHA-256. Compute SHA-1 too only when manifest export requires it.
  8. Reread the source and compare its digest again; check its stamp before accepting completion.
  9. Publish each healthy verified file without replacing unrelated existing data. Compatible publication has its own checksum/journal checks.
  10. After file and source-inventory completion, generate requested manifests, publish a new staged project, and save destination receipts. Record eligible pending report payloads for export-only retry.

FileStamp records device, inode, size and modification-time fields. The particular checks differ between plan validation, refreshed inventory checks and open-descriptor checks; they are not a single authenticated source-device identity protocol. SHA-256 remains the content acceptance reference once captured.

Concurrency, scheduling and memory

The source read/hash channel can queue two 8 MiB chunks. Each destination writer has its own two-chunk waiting queue, plus active data and other buffers. Bounds are independent of a single file's length, but peak memory is not universally 16 MiB: active workers, Data values, destination count, hashing, previews, file inventories and receipt tables all contribute.

Concurrent source processing is selectable from 1 to 4, default 2. Sources with intersecting discovered resource keys are merged transitively into serial groups. Each active source file can use up to four destination readback operations. That is a per-file limit, not a global promise of at most four verification threads.

StorageScheduler acquires sorted resource locks for destination write/readback operations. Discovery can add filesystem, whole-disk, physical-device and USB-ancestor keys. It does not measure USB bandwidth or control the transport controller. Not every source read is wrapped in the same resource lock; the implementation should not be described as a universal hardware scheduler.

More parallelism is not always faster. Several sources and destinations may compete on one reader, hub, SSD or APFS container. Bounded queues absorb short stalls; they do not allow a consistently slow direct-mode destination to lag arbitrarily far behind.

Publication and durability

On a volume supporting exclusive rename, a new project starts in a hidden staging directory and is renamed to the requested exact name after completion. Each verified file is moved exclusively within that project. Existing incremental projects can receive completed files before the entire job finishes.

For filesystems without the protected rename operation, the compatible path creates a new final file with exclusive creation, records its identity and digest in a publication journal, copies from the verified staging file, flushes and rehashes the final file, confirms the path still identifies the opened output, and retires staging data only after success. An interrupted owned final publication can be resumed after prefix checks. An unowned existing file is not adopted for writing.

The implementation uses fsync and F_FULLFSYNC at selected points, with explicit handling for unsupported drive-cache flush operations. Some directory flush results are best-effort. Storage hardware, filesystems, bridges and sudden power loss can still defeat assumptions; this is not a formal crash-consistency or power-failure guarantee.

Queue, resume and report recovery

TransferQueueStore writes immutable per-job plan JSON and atomically replaces queue metadata. It serializes access with a lock and flushes important files/directories. A previously running job restores as paused. No restored job starts automatically. Resume on one job runs that job; Start Queue deliberately runs queued work in order. A failed job stops further queue processing after healthy destinations in that job have had an opportunity to finish.

Resume never treats a saved completed flag or byte offset as proof. It rechecks sources, destination identity, existing files and partial prefixes. A completed primary with a valid cascade-ready marker can support backups without the original card, but the working copy is freshly checked before it is used.

A report failure is not the same as media corruption. When an eligible completed destination retains PendingReport.json, Retry Report Export can recreate its HTML/JSON receipt without source reads or media transfer. It locks the job workspace, checks ownership and destination identity, respects source/report overlap checks, and removes the pending record after export. Recovery payloads are limited to 128 MiB. This exports the frozen verification event; it does not reverify current files and does not regenerate an unsuccessful MHL export.

Reports, interchange and security

HTML presents outcomes, source/output paths, digests and advisories. JSON carries structured plan and receipt data with a schema identifier and app version. A per-destination report can contain verification rows for several destinations; its heading is destination-specific, and missing receipt rows are explicitly Not verified. New v3.7 destination success headings say Verified. Colors support the text rather than replacing it.

Optional exports are legacy MHL 1.1 and flat ASC MHL 2.0 using destination SHA-1 readback values. SHA-256 remains authoritative for ingest. SHA-1/MD5 support is for compatibility, not an assertion that they are suitable modern authenticity mechanisms. XXH64 is non-cryptographic and is only a supported comparison format here, not the ingest acceptance algorithm. xxHash project Full ASC directory hashes, root hashes and history references are not implemented; the verifier rejects those structures. The ASC ecosystem explicitly includes custody/history concepts beyond this flat export. ASC specification

Standalone verification accepts selected UTF-8 MHL documents or the app's SHA-256 JSON receipts, with a 128 MiB input limit. It checks listed paths relative to a user-selected root, detects missing/changed files, rejects unsafe traversal and links, rejects XML DTD/entity declarations, checks supported hashes, and reports unrecognized checksum fields as unsupported. It does not certify extra unlisted files.

Reports display in a native resizable WebKit window with JavaScript disabled and a nonpersistent website data store. Saved reports include filesystem paths, filenames and workstation-related metadata; review them before external sharing. They are not digitally signed, tamper-evident custody records, or encrypted archives. A user or compromised process with write access can alter a receipt and its hashes.

Progress and ETA

The recent copy/readback speeds sample separate byte counters at intervals of at least half a second. The older Avg I/O field combines copied and readback bytes over elapsed time. Neither number is a guarantee of raw device throughput. Speeds shown for stopped jobs are zero current speed, not a claim the transfer ran at zero speed.

ETA uses an exponentially smoothed work rate with an eight-second time scale and a three-second warm-up. The normal per-destination work budget is 4 × source bytes: source copy read, destination write, destination readback, and source reread. Compatible publication raises the modeled budget to 7 × bytes. Retained prefixes and reused files receive credits; publication work is modeled in coarse credits. Estimates expire in the queue after stale updates and are cleared on restoration.

Cascading initially estimates waiting backups using the working-copy rate and conservative sequential backup work; it then uses backup observations. Stage progress is mapped across primary and backup portions. Changing hardware rates, extra resume checks, OS caching, source inventory scans, manifest/report generation and unmeasured finalization mean this is an approximate job estimate, not a promised completion clock. No estimate is fabricated for a future unstarted queue of jobs.

This section is specific to OK, Copy 3.7, build 13. A capability being implemented is different from its being qualified on every filesystem, reader and failure scenario. These limits define the current product rather than promising a future feature date.

  • It is locally/ad-hoc signed, not Developer ID notarized. The development machine had no valid signing identity available. Clean-Mac installation and Gatekeeper behavior are not fully qualified.

Storage and topology

Network destinations are explicitly rejected by the planner. This is not a NAS-tuning or remote-sync application. Support for a locally mounted volume depends on the filesystem/driver permitting the required operations; “local” is not a blanket compatibility certificate for every device or bridge.

External/removable sources are protected at volume scope. Copying from one folder to another folder on that protected external volume is therefore rejected even when the folders do not overlap. Internal-folder source protection can be narrower. The restriction favors preserving original media over offering every generic file-copy arrangement.

Disk Arbitration/IOKit discovery is best effort. A reported shared disk/USB ancestor is useful, but an absent relationship does not prove independence. RAID, APFS arrangements, virtual disks, reader bridges and hubs can obscure topology. The scheduler does not build a complete transport bandwidth map, predict thermal throttling, or prove that backups use separate physical fault domains.

The app has no implemented card-lifespan, bad-block or wear telemetry dashboard. SD, CFexpress A and CFexpress B are filesystem sources here; use through a built-in SDXC slot or Ulanzi DC04 has not been comprehensively qualified. Hash equality is not a health or remaining-life assessment.

Verification and authenticity

SHA-256 is mandatory for ingest acceptance, but the reference must come from somewhere. Immediate jobs establish it during the first copy read; an unstarted immediate job has no preexisting content baseline capable of detecting a same-size, same-time change before that read. Review can establish an earlier baseline, at the cost of another source read.

Independent destination readback is an explicit second read operation. It is not a guarantee that macOS evicted its cache or that the device physically reread every cell. Flush calls also depend on filesystem, kernel and hardware behavior. There is no formal proof of crash consistency or survival of arbitrary power loss.

Receipts and source-reference files are not digitally signed or protected by a hardware trust anchor. A privileged or compromised process can tamper with local data and metadata. The application is not an adversarial forensic acquisition system or a hardware write blocker. It does not encrypt the copied files or reports.

Standalone verification checks the listed files, not the absence of extra files or the correctness of every possible manifest field/history. It supports the app's SHA-256 JSON receipts and selected flat MHL structures. Inputs must be UTF-8, within the 128 MiB limit, and contain safe paths. SHA-512, C4, XXH3/XXH128 and other unsupported algorithms do not become supported because a manifest names them.

ASC MHL and interoperability

Export is legacy MHL 1.1 and flat ASC MHL 2.0. The application does not create/validate a complete ASC chain, history graph, nested histories, directory/root hashes or digital signatures. Full chain-of-custody compliance is not claimed. One recorded XSD validation and local round trips do not establish interchange compatibility with every production application or every standards revision.

Ingest SHA-256 and exported SHA-1 serve different roles. Legacy SHA-1/MD5 comparison support is interoperability support, not a recommendation for new authenticity/security protocols. XXH64 support is not a cryptographic authenticity claim.

Performance, memory and estimates

  • No controlled head-to-head throughput or reliability benchmark against OffShoot, Copy That, Finder or rsync has been completed.
  • Mandatory extra reads and compatible final publication can be slower than a copy operation that does less verification. Optional Review adds work.
  • Queues are bounded per channel, but file inventories, manifests and receipts grow with file count. Very large numbers of small files can use substantial memory and preparation time.
  • Direct fan-out still waits for the slowest sustained writer once its queue fills. Cascading changes where work happens rather than eliminating the work.
  • Source concurrency is limited to four and source groups can be serialized. Destination readback concurrency is limited per active file and constrained by discovered shared locks.
  • Current-speed values are recent samples, not literally instantaneous hardware measurements. Average I/O combines different work from raw copy speed.
  • ETA is a modeled approximation. It includes source reads/rereads and coarse publication credits, but extra prefix checks, preparation, report/manifests, storage stalls and changing topology/rates can extend it. Cascading initially extrapolates backup speeds from the working drive. Unstarted jobs do not have a reliable whole-queue countdown.

Queue and interruption recovery

One queue job runs at a time. A failed job stops the queue after healthy destinations have had a chance to finish. There is no unattended policy engine that automatically chooses another backup destination or skips failed jobs forever.

Cancellation is cooperative. Waiting for blocked macOS device I/O can delay Stop or Pause and Quit. An idle-sleep assertion does not override lid-close, forced sleep, shutdown, device power loss or every OS policy.

Resume requires the saved plan and expected locations/identities. There is no general UI to relocate an immutable job to a new mount path, replace a lost destination with another drive, or edit its file mapping in place. Changed source inventories require a newly prepared plan. Healthy files are reverified on resume; this costs reading time.

Cascading can continue without the original card only after the primary reached its ready state and retained its reference data. It cannot reconstruct originals from an unverified, missing or changed working copy. Partial, rejected and hidden recovery files can consume space. Forget does not clean them up, and deleting them can remove recovery/report-export options.

Eligible report-only recovery replays a frozen HTML/JSON payload; it does not prove present-day file integrity, regenerate missing MHLs, or recover a receipt that was never saved. Its pending payload limit is 128 MiB. Reverify is the distinct action for a current check.

Reports and interface

History discovers app-local reports and report locations referenced by retained jobs. It is not a global indexed catalog of every report on all attached disks. Moving/removing report files or forgetting jobs can affect discoverability. Recovered report names can use a generic recovery identifier, and historical reports keep their original formatting and wording.

History Export saves the selected HTML report; it is not a complete media-plus-manifest archival package. Companion JSON/MHL files need to be preserved separately where required. Reports can disclose full paths, filenames, digests and workstation information; there is no built-in redaction or access-control management.

Quick Look previews depend on macOS and installed format support. There are no bundled professional camera SDKs or guaranteed thumbnails for every RAW/video format. The green/red presentation is accompanied by text, but full VoiceOver, keyboard-only, increased-contrast, light-mode and small-display coverage remains unfinished.

Native notification delivery depends on user permission and macOS notification policy. The app cannot guarantee a visible banner under Focus or other system restrictions.

Qualification still required

The 67 tests and 113 generated-file checks are useful evidence of modeled scenarios. They do not replace real SD/CFexpress, APFS/exFAT, many-small-file, disk-full, thermal, physical disconnect/reconnect, sleep and forced-power-loss tests with disposable data. Sustained performance and recovery need qualification on the actual Mac, reader, cables, hubs and destinations used in production.

These outstanding tests and Developer ID/notarization are current limitations, not completed features. See Validation for a practical qualification plan and the distinction between simulation and real hardware evidence.
